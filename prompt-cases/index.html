案例一：提示词给了模型一个「放弃」的出口 Case 01

这是我最想讲的一个案例——因为定位它靠的不是技术，而是一个对照实验。

01

现象：清晰的图，模型却说「无法识别」

提示词问题 模型没坏 对照实验
Situation 现象

用户发一张「西红柿炒鸡蛋」的示意图，模型返回四个字：无法识别。图很清晰，人一眼就能认出来。

Task 任务

先回答一个问题：是模型看不了图，还是我的用法有问题？不能急着换模型，换模型可能白花钱还不解决问题。

Action 行动 · 做对照实验

不动任何配置，只把提问换成中性问题：「这张图主要是什么颜色？」——同一个模型、同一张图。

原始提问

请只输出图里能看清的食材名称。
如果看不清或没有食材，
只输出四个字：无法识别
模型回答：无法识别

中性对照提问

这张图主要是什么颜色？
模型回答：红黄绿

图是传过去了、模型也看到了。再问「有哪些食材」，它给出了「红肉块、土豆块、南瓜块、葱花」。 所以是我的提示词把模型的嘴堵上了。

根因 · 我犯的具体错误

我在提示词里写了「看不清就只输出：无法识别」，本意是稳妥，实际等于 给了模型一个廉价的逃生出口——面对有歧义的图，它倾向于选那个被明确允许的安全答案。 这不是模型笨，是我在鼓励它偷懒。

Action 行动 · 改提示词

改之前

如果看不清或没有食材，
只输出四个字：无法识别

改之后

食材：<中文顿号分隔，尽量给出最可能的判断>
把握：<高 或 中 或 低>
即使图片不够清晰，也要给出你的最佳猜测。
同一张图回答：番茄、鸡蛋、葱（把握：高）
Result 结论（已沉淀为模板）

不要在提示词里给模型一个便宜的「我做不到」出口，要给它「尽力而为 + 标注置信度」的出口。 不确定性不该被藏起来，而应该显式地传出来，由上层流程决定怎么处理（比如请用户确认）。

案例二：输出「看起来合理」但有危害 Case 02

这个案例让我意识到：最危险的 bug 是不报错的那种。

02

海鲜过敏的用户，被推荐了「清蒸鲈鱼」

安全类偏差 不报错 需求理解错误
Situation 现象

输入：「我有虾仁和西兰花，但我海鲜过敏，能吃啥？」

系统识别出的食材是：虾仁、鲈鱼、三文鱼、西兰花 —— 多出来两个海鲜。最后给一个说自己海鲜过敏的人，推荐了清蒸鲈鱼。

为什么这个偏差特别危险

程序不报错、输出看起来还很合理——鲈鱼确实是海鲜、确实能做菜。 只有懂业务规则的人才能一眼看出问题，机器自己发现不了。 如果是真实用户，这不是体验问题，是可能进医院的问题。

根因 · 两层错

① 品类表里「海鲜」被定义成 [虾仁, 鲈鱼, 三文鱼]，用户说「海鲜过敏」时， 代码判断「海鲜」这个词出现在句子里，就把这三个全当成了用户手上的食材； ② 同义词表里有「鱼 → 鲈鱼」，「海鲜过敏」这句话里有「鱼」字，又匹配出一次鲈鱼。

本质问题是：我完全没有区分「用户有什么」和「用户不能吃什么」。

Action 改法 · 加否定语境判断

引入否定检测：食材名如果出现在「过敏 / 不吃 / 不能吃」这类否定词的同一个分句里， 就不算用户有的食材。同时检查前置否定（「不吃香菜」）和后置否定（「海鲜过敏」）—— 中文里「海鲜过敏」比「过敏海鲜」常见得多，只查一边会漏。

改的过程中还踩了两个小坑：否定窗口开太大跨过了逗号、误杀了用户真有的「西兰花」；只查前置否定、漏了后置否定。

Result 复测（4 组典型输入）
输入改前抽出改后抽出
我有虾仁和西兰花，但我海鲜过敏虾仁、鲈鱼、三文鱼、西兰花西兰花、虾仁
我对花生过敏，有鸡蛋和西红柿花生（误判为库存）+ 鸡蛋、西红柿西红柿、鸡蛋
不吃香菜，有土豆和青椒香菜 + 土豆、青椒土豆、青椒
海鲜过敏虾仁、鲈鱼、三文鱼（空）
Result 结论

① 安全和体验冲突时，永远选安全。我的判定偏向「只要有任意一次没被否定的出现就算用户有」—— 误判成「没有」最多少推荐一道菜，误判成「有」可能让人进医院。
② 这类 bug 不报错，必须靠回归用例焊死。修完后我补了一条断言：「海鲜过敏」不能抽出任何海鲜。

案例三：有些问题不是 bug，不能靠改代码解决 Case 03

这个案例教我的事：分清「模型能力不足」和「我的问题」，比修 bug 更重要。

03

同一张图、同一模型，三次给出三份不同的食材清单

模型固有不确定性 不是 bug 用流程兜底
Situation 现象

带照片提问时：第 1 轮识别出「西红柿、鸡蛋、小葱」，请用户确认；用户说「对的，就这些」； 结果第 2 轮模型说「那就按土豆 + 西红柿来配」—— 土豆是哪来的？用户刚确认过的清单被改掉了。

Action 排查 · 先排除自己的问题
检查项结果
单独测分词器 extract("番茄、鸡蛋、葱")返回正确：西红柿、鸡蛋、小葱
打印视觉模型逐轮原始输出三次三份清单

逐轮看模型原始输出：

调用模型返回
第 1 次番茄、鸡蛋、葱（把握：高）
第 2 次红甜椒、黄甜椒、葱花或香菜碎、番茄、土豆、菠萝（把握：低）
第 3 次又是另一份

「土豆」是模型自己说的，我的代码一个字都没错。这是模型对模糊图像固有的不确定性，换个模型也只是程度不同。

Action 处理 · 不修代码，改产品流程

技术消除不了这个不确定性，所以在产品层面加一道「识别结果请用户确认」： 用户花 3 秒确认，换来的是系统不会拿着错误的前提一路推下去。 并且在提示词里明确写：用户确认过的清单要牢牢记住，后续不要重新识别。

Result 结论（这个项目最大的收获）

能用代码解决的用代码，代码解决不了的用流程，流程也兜不住的用交互。 三个案例正好是这三层：
案例二 = 代码层（加否定检测）；案例一的提示词问题 = 流程层（把软约束写成显式规则）； 案例三 = 交互层（让用户确认）。

28 个测试用例 Test Suite

把「推荐得准不准」这种主观感觉，拆成可以判定对错的断言。分两类：一类查数据一致性，一类查行为回归。

抽取与查询理解

12 个
  • 最基本的食材抽取
  • 同义词要能归一化
  • 品类词要能展开
  • 能剥掉用量数字
  • 忌口食材不能进库存
  • 品类否定 · 海鲜过敏
  • 前缀否定
  • 不能吃虾
  • 否定不能跨分句误伤
  • 重复食材只算一次
  • 空输入不炸
  • 没有食材的句子

检索、排序与过滤

16 个
  • 时间过滤
  • 难度过滤
  • 纯素过滤
  • 分类过滤
  • 过滤条件互斥时返回空而不是报错
  • 食材全匹配的菜要排在前面
  • 用上更多食材的菜优先
  • 完全匹配的两样食材要排最前
  • 有库存时不能推一样都用不上的菜
  • 缺料要如实报告
  • 关键词检索生效
  • 无库存时退化为纯文本检索
  • 相同输入结果稳定
  • 虾仁是海鲜
  • 蚝油里的海鲜只算痕量而不是实锤
  • 北豆腐含大豆
批量测试的真正价值

我调过三次排序权重。每次改完跑一遍脚本，就知道有没有把效果调坏—— 没有批量测试，只能靠肉眼一条条看，改一次心虚一次。有了它，你敢改。

从这些案例里沉淀的 5 条规范 Prompt Spec

这些是我自己踩坑总结出来的，也是我认为可以直接复用到别的 AI 产品上的部分。

  1. 不给「我做不到」的出口。把「看不清就输出无法识别」换成「尽力判断 + 标注置信度」，模型立刻愿意干活。
  2. 确定性的事交给代码，模糊理解才交给模型。算营养、判过敏这类「算错会出事且有唯一答案」的事，不能给概率模型做。
  3. 不确定性要显式标出来，不要藏着。让模型输出把握程度，由流程决定要不要请用户确认。
  4. 安全约束要写成显式规则 + 代码兜底。提示词是软约束，模型可能不遵守；安全相关的必须有硬性路径。
  5. 每条提示词改动都要有回归用例兜住。否则改一处坏一处，而且你不会发现。
